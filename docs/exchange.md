# 대학 간 학점교류 수강신청

학생이 우리 대학 포털에서 상대 대학 강좌를 신청합니다. 우리 서비스는 학점과 시간표를 관리하고 상대 대학은 자기 강좌의 좌석을 관리합니다. 상대 대학 좌석을 예약한 뒤 우리 대학 신청을 저장하고 외부 예약을 확정해야 신청 완료입니다.

## API와 책임

- `POST /api/exchange-enrollments`: `{ "studentId": 1, "courseId": 1 }`, `Idempotency-Key` 필수. `200`은 완료, `202`는 복구를 포함한 처리 중, `409`는 최종 취소입니다.
- `GET /api/exchange-enrollments/{requestId}`: 처리 상태 조회. 조회 성공 HTTP 200 자체가 수강신청 완료를 뜻하지 않습니다. `phase=COMPLETED`를 확인합니다.
- 학생과 멱등 키가 같으면 같은 requestId를 반환합니다. 강좌가 다르면 `IDEMPOTENCY_KEY_REUSED`입니다. 취소된 요청도 보존하며 새 신청에는 새 키가 필요합니다.
- 상대 대학 API는 `GET /reservations/{id}`로 상태 조회, `PUT`과 `action=reserve|confirm|cancel`로 변경합니다. 요청 ID와 학생/강좌를 결합한 멱등 계약입니다.
- 기존 `/api/enrollments`는 읽기 전용 자격 검증을 사용한 락 비교 실험용 경로로 유지합니다. 실제 학점교류 사용자는 새 경로만 사용해야 합니다. 두 API를 같은 학점교류 강좌에 섞어 공개하는 운영 구조가 아닙니다.

## 상태와 복구

| 상태 | 남아 있는 효과 | 다음 동작 |
|---|---|---|
| RESERVING | 요청 의도 기록. 외부 예약은 없거나 결과 불명 | 외부 상태 조회 후 없을 때만 동일 ID로 예약 |
| CONFIRMING | 외부 임시 좌석과 로컬 수강 좌석 확보 | 확정 상태 조회 또는 같은 ID로 확정 |
| COMPLETED | 양쪽 확정 | 동일 결과 반환 |
| CANCELLING | 로컬 신청 없음. 외부 예약 취소 필요 | 멱등 취소 재시도 |
| CANCELLED | 로컬 신청 없음. 외부 좌석 없음 | 취소 결과 반환 |

외부 HTTP 대기는 DB 트랜잭션 밖입니다. Redis 강좌 락은 외부 예약부터 짧은 로컬 저장까지 조절하고 확정/취소는 요청별 멱등 API로 처리합니다. JVM별 공정 세마포어가 Redis 경합을 줄입니다. Redis는 외부 대학의 다른 클라이언트까지 통제하지 않으므로 외부 서버도 정원과 중복 예약을 원자적으로 검증합니다.

로컬 신청, 학생/강좌 CAS, 성공 멱등 레코드와 `CONFIRMING` 전환은 같은 DB 트랜잭션입니다. 따라서 DB 커밋 응답이 끊겨도 복구기가 DB 상태를 읽고 다음 동작을 결정합니다. `CONFIRMING` 중인 신청도 학점과 시간표와 정원에 포함해 다른 신청이 자리를 가져가지 못하게 합니다.

DB에 기록한 요청을 두 JVM의 복구기가 2초 간격으로 찾습니다. UUID 소유자와 30초 claim으로 같은 요청의 중복 처리를 줄입니다. claim 만료 후 다른 JVM이 인계할 수 있고 로컬 커밋은 요청 행을 짧게 잠근 뒤 현재 소유자와 유효기간을 확인합니다. 모든 외부 변경은 중복 호출을 허용하는 상태 전이이므로 이전 실행의 늦은 응답도 새 예약을 만들지 않습니다. claim은 강좌 DB 락을 외부 호출 동안 잡는 구조가 아닙니다.

## 실패를 어떻게 해석하나요?

- 예약 응답 타임아웃: 실패 확정이 아닙니다. `RESERVING`을 유지하고 같은 ID로 외부 결과를 조회합니다.
- 로컬 시간표/학점/중복 거절: 로컬 저장은 롤백됩니다. `CANCELLING`을 먼저 기록한 뒤 외부 예약을 취소합니다. 취소 응답이 끊겨도 재시도합니다.
- 외부 확정 응답 타임아웃: 로컬 신청을 삭제하지 않습니다. 외부에서는 확정됐을 수 있으므로 `CONFIRMING`에서 조회 후 복구합니다.
- Redis TTL 만료: 감지 시 로컬 트랜잭션을 롤백합니다. 외부 임시 예약은 남을 수 있으며 지속된 요청 의도를 통해 다시 처리합니다. TTL은 DB 롤백 명령이 아닙니다. 마지막 검사와 커밋 사이의 틈은 기존 CAS/UNIQUE/정원 조건이 보호합니다.
- 프로세스 중단: 요청은 MySQL에, 외부 예약은 파트너 시뮬레이터 SQLite 볼륨에 남습니다. claim 만료 후 재처리합니다.
- 외부 상태 모순: `PARTNER_STATE_MISMATCH`로 처리 중 상태를 유지하고 로그에 기록합니다. 임의로 완료/취소하지 않습니다.

로그 `event=exchange_retry`에는 request ID와 원인이 남습니다. `PARTNER_CONNECT_TIMEOUT`은 연결 단계, `PARTNER_RESPONSE_TIMEOUT`은 응답 대기, `PARTNER_IO_ERROR`는 통신 실패, `LEASE_LOST`는 Redis 소유권 상실입니다. DB 장애는 예외 유형으로 기록합니다. 요청 조회의 `lastError`와 `attempts`, `updated_at`으로 장기 미해결 건을 확인할 수 있습니다. 취소 중에는 원래 업무 거절 사유를 유지하고 취소 통신 실패는 로그에 기록합니다.

## 시뮬레이터 계약과 한계

실제 대학 연동이 아닌 직접 만든 상대 대학 시뮬레이터입니다. 예약은 SQLite 트랜잭션으로 정원을 지키고 같은 학생/강좌의 이중 좌석 확보를 차단합니다. 취소 이력을 지우지 않아 늦게 도착한 예약 요청이 자리를 되살리지 못합니다. 확정된 예약은 이 예제에서 취소 불가입니다.

**임시 예약은 자동 만료되지 않고 명시적 확정/취소까지 유지된다는 계약**입니다. 장기 장애 동안 좌석이 점유될 수 있는 비용을 감수합니다. 실제 상대 대학이 TTL 예약만 지원한다면 로컬 임시 신청 만료와 학점/정원 복원까지 추가해야 하며 현재 구현을 그대로 연결할 수 없습니다. 복구 재시도는 자동으로 지속되며 영구 오류의 운영자 해결 화면이나 알림은 구현하지 않았습니다.

서로 다른 요청 키로 동시에 같은 강좌를 신청하면 외부 중복 예약 거절을 `FULL`로 표현합니다. 실제 API에서는 중복/정원 초과를 별도 코드로 나누는 것이 적절합니다. 인증과 학생별 조회 권한은 미구현이므로 공개 운영용 API가 아닙니다.

## 검증 및 실행

```bash
python -m unittest discover -s scripts -p 'test_*.py'
mvn -f backend/pom.xml verify
# 부하 실험은 기존 데이터를 삭제하므로 전용 실험 DB에서만 실행합니다.
mvn -f backend/pom.xml -DskipTests package
docker compose up -d --wait mysql redis external
pip install requests pymysql aiohttp
python scripts/exchange_benchmark.py
```

파트너 예약 볼륨도 실험마다 비어 있어야 합니다. 이 부하 스크립트는 로컬 DB를 초기화하지만 외부 기록은 삭제하지 않습니다. CI는 매번 새 볼륨으로 실행합니다. 기존 외부 볼륨을 재사용하면 이전 확정 좌석 때문에 정원 검증이 실패하도록 했습니다.

테스트는 예약 결과 불명 후 재조회, 확정 응답 유실 후 복구, 로컬 거절과 취소 재시도, 동일 키 동시 요청, claim 인계, Redis 소유권 상실을 확인합니다. HTTP 클라이언트 테스트는 실제 HTTP 서버가 예약 효과를 기록한 다음 응답을 늦추는 상황을 재현합니다. 외부 저장소는 병렬 정원 검증과 재시작 후 멱등성과 취소 tombstone을 검증합니다.

새 부하는 두 JVM에 동시성 128로 서로 다른 신청 12,000건을 보냅니다. `202`를 성공으로 세지 않고 모든 요청이 최종 상태에 도달한 뒤 로컬 6,000건과 외부 확정 6,000건을 요청별 대조합니다. 100건의 같은 키 재전송도 확인합니다. 이것은 예약 시나리오 정합성 검증이며 세 락 방식의 새 성능 비교가 아닙니다. 기존 216,000건 성능 수치는 읽기 전용 API 실험에만 해당합니다.
