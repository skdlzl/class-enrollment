# 실측 결과와 Redis 채택 판단

측정일: 2026-10-29 KST. [최종 CI 실행](https://github.com/skdlzl/class-enrollment/actions/runs/40739204179), 검증 코드 `39c87d6232b8d2f8ee99426ff391eeabb4532715`. 이후 결과 문서 변경은 이 코드와 구분한다.

## 결론

**Redis 조율 방식을 기본 전략으로 채택한다. 근거는 집중 부하에서의 실패 억제, 외부 API 재호출 감소, DB 커넥션 대기 감소다.** 최종 Redis 72,000건에서 503은 0건이었다. 단, 비관적 락보다 처리량이나 성공 응답 P95가 우수하다는 결과는 나오지 않았다. “세 방식 중 무조건 가장 빨라서 선택했다”는 표현은 이 측정으로 뒷받침할 수 없다.

외부 API는 지연 20ms의 읽기 전용 시뮬레이터다. 비교 대상 DB 전략은 외부 호출 동안 DB 트랜잭션을 유지한다. 따라서 이 결과는 외부 호출을 포함한 조율 구조의 비교이며, 외부 호출을 트랜잭션 밖으로 옮긴 다른 DB-only 구현까지 포함한 일반적인 우열은 아니다.

## 최종 비교

JVM 2개, JVM당 Hikari 20개, 동시 요청 128개, 회차당 12,000건. 세 전략 × 두 부하 × 세 회차로 216,000건을 보냈다. 54,900건을 실제 신청으로 저장했고 모든 회차에서 정원·신청 내역·멱등 결과 수가 일치했다. 정원 마감 409는 정상적인 업무 거절이며 아래 503과 구별한다.

아래 시간은 세 회차·두 JVM의 Micrometer 누적값에서 워밍업 직후 값을 뺀 합계다. 여러 요청이 동시에 자원을 사용하므로 벽시계 실행시간보다 클 수 있다. 평균 응답시간이 아니다.

## 타임아웃과 실패의 실제 원인

1. **비관적 집중 부하 306건:** HTTP 코드 `DB_CONNECTION_UNAVAILABLE` 306건과 Hikari timeout 카운터 증가 306건이 일치한다. 따라서 이 실행에서는 단순히 DB가 꺼진 것이 아니라 커넥션 획득 제한 1초 소진으로 분류할 근거가 있다. 외부 호출과 행 잠금 대기 동안 커넥션을 유지하는 구조가 풀 압박을 만든다. 별도로 DB 행 잠금 제한에 걸린 재시도는 20회이며, 이를 HTTP 실패 306건에 추가로 더하면 안 된다.

2. **낙관적 집중 부하 1,105건:** 1,104건은 `RETRY_EXHAUSTED`, 1건은 DB 커넥션 획득 실패다. VERSION_CONFLICT 재시도는 11,060회였다. 버전 충돌이 전체 트랜잭션 및 외부 자격 조회 재실행으로 이어졌고, 8회 제한을 넘은 요청은 503으로 종료됐다. 이 재시도 소진을 외부 응답 timeout이나 DB deadlock으로 바꿔 부르지 않는다.

3. **개선 전 Redis 집중 부하 118건:** `REDIS_LOCK_TIMEOUT`이다. 원본 로그에는 `elapsed_ms=5000`, `5003`, `5005`, `5009` 같은 표본이 있고 DB 풀 timeout은 0이었다. 마감 후에도 락을 먼저 얻던 흐름과 비공정 SET NX 폴링으로 요청 입장 예산 5초를 소진했다. 과목의 외부 호출 20ms만으로도 정원 100명을 처리하는 데 최소 2초가 들고, DB 처리·Redis 왕복·대기 경쟁이 더해졌다.

4. **개선 후 Redis:** 로컬 입장/Redis 입장/외부 호출/DB 오류를 포함한 503은 72,000건에서 0건이다. 이는 해당 부하 조건의 결과이며 Redis 장애나 무제한 트래픽에서도 오류가 없다는 보장은 아니다. TTL 만료·소유자 교체·외부 응답 지연은 아래 별도 실패 주입 테스트로 확인했다.

## 기능·장애 검증

JUnit 27개가 실패·오류·스킵 없이 통과했다. MySQL 8.4와 Redis 7.4 실제 컨테이너를 사용한다.

- 세 전략의 정원, 동일 키 동시 재요청, 키의 다른 과목 재사용, 중복 신청.
- 같은 학생의 서로 다른 과목 요청을 외부 검증 구간에서 맞춰 시간표 충돌·학점 초과 방지.
- 마지막 좌석과 멱등 재전송이 경합할 때 같은 신청 ID 반환.
- 외부 검증 뒤 Redis 소유자가 바뀌면 저장하지 않고 새 소유자의 락도 삭제하지 않음.
- DB 트랜잭션 도중 실제 TTL 만료를 유도하고 신청·정원·멱등 키 전체 롤백 확인.
- 외부 timeout 뒤 같은 키 재시도, 실제 HTTP 응답 지연, 비정상 상태와 끝나지 않는 본문 처리.
- 로컬 입장 제한시간, 인터럽트 보존, permit 중복 해제 방지.

마지막 TTL 검증과 실제 DB commit 사이에 만료될 수 있다는 경계는 남는다. 이 경우 “만료된 작업은 절대로 commit되지 않는다”고 주장하지 않으며, DB 버전 CAS·정원 조건·UNIQUE가 정합성을 보장한다. 자세한 계약은 [설계 문서](design.md)를 따른다.
