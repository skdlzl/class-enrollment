# Windows 조건부 UPDATE 재측정 결과

## 결론

Windows에서도 조건부 UPDATE가 기존 Redis 과목 락보다 빨랐다. JVM당 연결 10개 조건에서 평균 응답시간은 **7.9초 → 6.1초**, 조건별 1,500건을 합쳐 계산한 P95는 **10.2초 → 8.4초**였다. Redis 구현의 락 획득 시간 초과 503은 547건이었고 조건부 UPDATE에서는 0건이었다.

조건부 UPDATE의 주요 지연 구간은 DB 연결 확보였다. 전체 평균 6.089초 중 연결 확보 평균이 5.389초로 약 88.5%를 차지했다. DB 연결 수를 늘리면 연결 확보 대기는 줄었지만 같은 과목 UPDATE의 잠금 경쟁이 커졌다.

과거 Windows에서 기록한 22.3초는 이번 측정에서 재현되지 않았다. 과거 수치는 유지하되 조건부 UPDATE의 일반적인 성능이나 이번 실행의 결과와 구분한다. 이번 증거에 맞춰 조건부 UPDATE를 일괄적으로 '느려서 제외한 대안'이라고 설명한 판단은 수정한다.

## 검증 범위와 환경

입력 파일: `windows-atomic-20261012-154602.zip`, Windows 사용자 PC에서 2026-10-12 측정.

- Windows 11 Home, Intel Core i5-8250U, 물리 코어 4개 및 논리 CPU 8개, RAM 약 8GB
- Docker에 표시된 CPU 8개, 메모리 상한 약 4GB
- 실제 Java 21.0.2. JVM 2개, 각 JVM `-Xms256m -Xmx512m`
- MySQL 8.4.11, REPEATABLE READ, `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`
- Redis 7.4, JMeter 5.6.3. 같은 PC에서 JVM/DB/Redis/JMeter 실행
- 로그 수준은 양쪽 모두 root WARN. 같은 JDBC 관찰 코드와 GC 파일 로그 적용
- 동일한 학생 500명, 과목 1개, 정원 100명. 500건을 5초 동안 시작하고 2개 JVM에 번갈아 요청
- 실행마다 JVM 재시작, 성공 요청 20건으로 준비한 뒤 신청 내역과 인원수 초기화
- 각 조건 3회. 짝수 회차는 비교 순서를 반대로 진행
- Redis 업무 구현 고정 커밋: `6ebba4d65808e947bc67a0e39afacfec66e51443`
- 조건부 UPDATE 업무 구현 고정 커밋: `d2c9aec979ec1aca7e23b4e935dcd2a0edd32007`

9회 모두 원본 JTL 500건의 상태 코드, 평균, P95를 재계산해 `summary.json`과 일치함을 확인했다. 각 JVM의 서버 식별 자료에 측정 폴더와 포트가 일치했다. 모든 회차 `ObservationComplete=true`와 `Consistent=true`였다.

원본 ZIP의 SHA-256과 환경은 [windows-metadata.json](atomic-update-evidence/windows-metadata.json)에 보관했다. 사용자 이름이나 임시 소스 경로 등은 별도 공개 자료에 포함하지 않았다.

## 전체 응답 결과

각 조건은 500건씩 3회로 총 1,500건이다. 평균은 요청 수가 동일하므로 회차 평균의 산술평균과 전체 1,500건의 평균이 같다. 아래 P95는 **원본 JTL 1,500건을 합쳐 다시 계산한 값**이다.

| 조건 | 평균 | 전체 1,500건 P95 | 201 | 409 | 503 |
| --- | --- | --- | --- | --- | --- |
| Redis 과목 락, 연결 10개/JVM | 7.937초 | 10.201초 | 300 | 653 | 547 |
| 조건부 UPDATE, 연결 10개/JVM | 6.089초 | 8.390초 | 300 | 1,200 | 0 |
| 조건부 UPDATE, 연결 50개/JVM | 6.285초 | 7.847초 | 300 | 1,200 | 0 |

연결 10개 조건끼리 비교하면 평균은 약 23.3%, 합산 P95는 약 17.8% 감소했다. Redis 구현의 503 응답 본문은 모두 `LOCK_ACQUISITION_TIMEOUT`이었다. 조건부 UPDATE의 409 본문은 모두 `COURSE_FULL`이었다.

모든 회차 성공 건수 100건과 DB 신청 내역 및 `enrolled_count` 100명이 일치했다. 정원 초과 및 인원수 불일치는 없었다.

## 구간별 대기

아래 값은 동일한 구간의 회차별 평균을 평균한 값이다. 두 조건부 UPDATE 설정 모두 회차마다 연결 확보 기록이 500개여서 요청 전체 평균과 직접 비교할 수 있다.

| 조건 | DB 연결 확보 평균 | UPDATE 실행 평균 | DB 연결 사용 평균 | JVM당 연결 대기자 관찰 최대 | DB 잠금 대기자 관찰 최대 |
| --- | --- | --- | --- | --- | --- |
| Redis 과목 락, 연결 10개/JVM | 0.000354초 | 0.004773초 | 0.034821초 | 0명 | 0명 |
| 조건부 UPDATE, 연결 10개/JVM | 5.388977초 | 0.325646초 | 0.439785초 | 190명 | 18명 |
| 조건부 UPDATE, 연결 50개/JVM | 3.836743초 | 1.902874초 | 2.082715초 | 150명 | 98명 |

UPDATE 시간에는 DB 행 잠금 대기, SQL 처리와 통신이 포함된다. 연결 사용 시간은 연결을 확보한 뒤 반납할 때까지이며 UPDATE 시간도 그 안에 포함된다. 이 두 시간을 서로 더해 전체 시간으로 계산하지 않는다.

조건부 UPDATE 요청은 DB 연결을 확보한 상태에서 같은 과목 행을 수정할 차례를 기다렸다. 사용 중인 연결이 반납되지 않으므로 다른 요청은 연결 확보 단계부터 기다렸다. 연결 10개/JVM에서는 전체 평균 6.089초 중 연결 확보에 5.389초를 사용했다.

연결을 50개/JVM으로 늘리자 연결 확보 평균은 5.4초에서 3.8초로 줄었지만 UPDATE 평균은 0.3초에서 1.9초로 증가했다. 실제 MySQL 잠금 기록의 대상은 모두 과목 ID 1의 `courses` PRIMARY 행이었고 `X,REC_NOT_GAP` 대기가 기록됐다.

DB에 진입할 수 있는 요청 수를 늘려도 같은 과목 행을 동시에 수정할 수 있는 수가 늘어나지는 않았다. 대기가 연결 풀 밖에서 DB 안으로 이동한 양상을 확인했다. 풀 50개에서 전체 평균은 소폭 증가했고 합산 P95는 소폭 감소했다. 전체 평균과 P95의 변화 방향이 달랐다.

각 JVM의 전체 실행 동안 GC 정지 시간 합계는 약 0.21~0.32초였고 가장 긴 개별 정지는 약 0.064초였다. 수초 단위 지연을 직접 설명하는 주요 관측 구간은 DB 연결 확보와 UPDATE였다. OS 페이징이나 디스크 대기의 기여도는 별도로 측정하지 않았다.

회차 P95의 평균은 Redis 10.266초, UPDATE 연결 10개 7.463초, UPDATE 연결 50개 7.328초다. 이 값은 합산 P95와 계산 방식이 다르다. 성과를 설명할 때 위 전체 응답 표의 합산 P95를 사용한다.

풀 50개와 10개의 평균 차이는 약 0.2초이며 회차별로 우열이 바뀌었다. 연결 수 설정의 효과는 평균과 P95를 각각 확인한다. 반복적으로 확인된 변화는 연결 확보 대기 감소와 같은 과목 UPDATE 대기 증가다.

## 설계 설명에 반영할 판단

조건부 UPDATE로 정원을 제어하면서 정합성을 유지했다. 동일한 Windows 조건에서 기존 Redis 과목 락보다 평균과 P95가 줄고 락 획득 시간 초과가 사라졌다. 요청을 DB에서 처리하는 방식으로 바꾸면서 DB 연결과 행 잠금 대기가 새로운 병목으로 나타났다.

연결 수를 늘리는 것과 같은 과목의 처리량을 늘리는 것은 구분한다. 앞으로 이 데이터를 설명할 때는 정원을 지키는 방법과 요청이 기다리는 위치 및 사용하는 자원 사이의 트레이드오프를 중심으로 정리한다.

이 비교의 기준은 원래 `feat/redisson-lock`이다. 락 범위를 줄인 버전이나 로컬 대기열 후보와의 직접 비교 결과로 대체하지 않는다. 업무 구현을 채택 브랜치에 병합하거나 Notion 포트폴리오를 자동 변경하지 않았다.
