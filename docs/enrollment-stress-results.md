# 대량 신청의 접수와 결과 확인을 분리한 이유

> 이 결과는 비동기 접수와 동기 처리 구조의 비교입니다. Redisson 분산락과 MySQL 비관적 락의 우열을 입증하지 않습니다. 과목 락 비교는 [동기 락 비교](sync-lock-comparison.md)에서 별도로 진행합니다.

## 포트폴리오용 요약

대량 신청에서 HTTP 응답을 기다리는 부담을 줄이기 위해 Redis 기반 비동기 접수 구조를 선택했습니다.
회당 5,000건을 3회 측정해 모든 신청의 최종 결과를 확인했습니다.
동기 방식에서는 일부 요청이 클라이언트 시간 초과로 결과를 확인하지 못했습니다.
다만 비동기 구조는 조회 지연과 폴링 부하가 늘어나는 비용이 있었습니다.

## 비교 결과

| 항목 | Redis 비동기 접수 | 비관적 과목 락 + 로컬 대기열 |
|---|---:|---:|
| 최종 결과 확인 / 계획 15,000건 | 15,000 | 11,265 |
| 응답 불명 | 0 | 3,733 |
| 503 | 0 | 2 |
| 확정 결과 확인 P95 범위 | 9.5~24.1초 | 2.3~6.5초 |
| 거절 결과 확인 P95 범위 | 14.8~35.2초 | 57.1~58.2초 |
| 혼합 구간 조회 P95 범위 | 331~1,290ms | 8~42ms |
| 정원 초과 | 없음 | 없음 |

P95 범위는 회차별 값의 최솟값~최댓값입니다. 조회는 두 서버 값을 모두 포함합니다.
원시 요청을 합쳐 계산한 전체 P95가 아닙니다. 응답 불명은 DB 처리 실패를 의미하지 않습니다.
거절 시간은 거절 응답을 확인한 요청만 포함하므로 시간 초과 요청을 제외한 수치입니다.

## Redis와 락의 역할

Redis는 접수 상태 저장, 비동기 처리 대기, 여러 서버의 워커 동시 실행 수 조절에 사용했습니다.
정원 및 학생 제약의 최종 보호는 워커의 DB 트랜잭션과 행 잠금이 담당합니다.
따라서 결과는 Redis 분산락 알고리즘과 MySQL 행 잠금의 단독 성능 비교가 아닙니다.
동기 비교 경로에도 학생 단위 Redisson 락이 남아 있습니다.

## 실험 조건과 해석 범위

- 로컬 애플리케이션 2개, Hikari 풀 서버당10, 정원100. 계획 부하는 신청5,000건/5초와 조회 서버당50RPS.
- Node HTTP 연결 풀은 서버당 접수128, 조회16, 폴링32, 진단2. 두 방식에 같은 제한 적용.
- Redis 접수는 HTTP10초 제한, 최종 결과 관찰60초. 동기는 최종 HTTP 응답까지60초 제한.
- 접수202는 확정이 아님. Redis의 최종 결과 확인 시간에는2초 폴링 간격과 폴링 연결 대기가 포함됨.
- 연결 수 제한이 실제 서버 도착량을 조절함. 5,000건이5초 안에 서버에 도착했다고 주장하지 않음.
- 각 baseline/mixed는90초이며 본문 조회 P95는 시작5~70초 구간. 집중5초 결과는 results.json의 burstReads에 별도 보존.
- Redis2회차 조회 생성 누락1건 포함. 요청 생성 누락은 모든 회차0, 관측된 조회 HTTP 실패는0.
- 회차 도중 재시작 절차 안내가 바뀌었음. 모든 회차의 JVM 예열 상태가 동일하게 통제됐다고 주장하지 않음.
- PC 자원 공유와 제한된 클라이언트 연결의 영향을 포함한3회 관찰 결과. 실서비스 처리 한계나 무손실 보장을 입증한 실험이 아님.

선택 근거는 이번 조건에서 대량 신청의 최종 결과를 모두 확인한 점입니다.
조회 지연 감소, 확정 응답 속도, Redis 분산락 자체의 우위는 이 실험의 성과로 주장하지 않습니다.
