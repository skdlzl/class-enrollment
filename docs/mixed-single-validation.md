# 혼합 구성의 중복 사전 검증 제거

## 변경 이유

장애 대응을 보완한 뒤 혼합 구성은 읽기 전용 사전 검증과 저장 트랜잭션에서 학생 상태, 중복 신청, 학점, 시간표를 두 번 검사했습니다. 최종 검증은 학생 DB 락 안에서 수행하므로 혼합 구성의 별도 사전 검증은 제거합니다.

## 처리 순서

학생 Redis 락 → 저장 트랜잭션 시작 → 학생 DB 락 → 학생 및 과목 조회와 규칙 검증 → 과목 DB 락 및 현재 정원 재확인 → 저장 및 커밋 → 학생 Redis 락 해제.

혼합(PESSIMISTIC)에서만 validateForEnrollment 호출을 제거했습니다. REDIS의 과목 Redis 락 전 사전 검증과 DB_ONLY 경로는 변경하지 않았습니다. 로컬 대기열 설정도 변경하지 않았습니다.

## 유지한 안전장치

- Redis 락이 만료돼도 학생 DB 락 아래에서 최신 신청 내역으로 검증합니다.
- 과목 DB 락과 현재 값 조회를 유지해 정원 초과를 방지합니다.
- 커밋 이후 Redis 락 해제와 응답 유실 확인 API를 유지합니다.
- 중복 저장 제약과 DB 오류 응답 처리를 유지합니다.

## 기대 효과와 한계

사전 검증을 통과해 쓰기까지 진행하는 혼합 요청에서 별도 읽기 트랜잭션 1회와 학생 조회, 과목 조회, 검증 집계 쿼리 3회를 제거합니다. 실패 요청의 감소량은 거절 시점에 따라 다릅니다. 최종 검증은 과목 DB 락을 획득하기 전에 실행됩니다.

성능 개선 수치는 아직 측정하지 않았습니다. 과목 DB 락 대기 중 연결 점유는 남습니다. 서로 다른 학생의 요청만 발생하는 실험에서는 학생 Redis 락의 대기 분산 효과도 제한적입니다. 이번 변경만으로 순수 DB보다 빠르다고 주장하지 않습니다.

## 검증 및 재측정

기존 장애 안전성 CI를 실행해 락 만료, JVM 강제 종료, 롤백, 응답 유실 및 동시 신청을 재검증합니다. 예열을 제외한 본 측정에서 신청 완료율, 완료 시간 P95, 조회 P95, 전송 생략을 함께 비교합니다. 기존 결과를 새 코드의 성능 근거로 재사용하지 않습니다.
