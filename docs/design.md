# 동시성 설계

## 보호 대상

- 과목: 정원, 외부 API 호출의 과목별 동시 실행.
- 학생: 동일 학기 학점/시간표. 별도의 Redis 학생 락 대신 `students.version` CAS를 사용한다.
- 신청: `(student_id, course_id)` UNIQUE.
- 성공 응답: `(student_id, request_key)`에 과목 ID와 신청 ID를 같은 트랜잭션으로 저장한다. 키는 대소문자를 구별한다.

## 세 전략

|전략|외부 호출 시 DB 자원|충돌 처리|
|---|---|---|
|PESSIMISTIC|과목 SELECT FOR UPDATE와 커넥션 유지|행 잠금 대기 + 학생 CAS 재시도|
|OPTIMISTIC|스냅샷 트랜잭션과 커넥션 유지|과목·학생 CAS 실패 시 전체 재시도|
|REDIS|Redis 과목 락만 유지, DB 트랜잭션은 외부 응답 후 시작|짧은 트랜잭션의 과목·학생 CAS, 만료 검증|

이 비교는 단순 락 라이브러리 속도가 아닌 **외부 호출을 포함한 조율 구조**의 비교다. DB의 짧은 UPDATE 잠금까지 없앴다는 의미가 아니다. 더 강한 대조군으로 외부 호출을 트랜잭션 밖으로 뺀 DB-only 방식도 실험해야 일반적인 Redis 우위를 말할 수 있다. 외부 자격 조회 자체는 읽기 전용이므로 Redis가 업무상 필수라는 주장도 하지 않는다.

## 학생 락을 제거해도 되는 이유

학생의 버전을 읽고, 동일 스냅샷에서 학점·시간표를 검증한다. 커밋 전에 `UPDATE students SET version=version+1 WHERE id=? AND version=?`를 수행한다. 같은 학생의 두 트랜잭션 중 하나만 해당 버전을 갱신할 수 있다. 패자는 과목 인원 갱신까지 전부 롤백하고 **새 트랜잭션**에서 재검증한다. 따라서 서로 다른 과목 락을 얻은 요청끼리도 write skew를 방지한다. 과목 → 학생 → 신청 INSERT 순서를 고정한다.

시간표는 같은 학기만 비교하고 [시작, 종료) 구간을 사용한다. 09:00~10:00과 10:00~11:00은 충돌하지 않는다. 학점도 학기별 합산이다. 현재는 신청만 지원한다. 취소·관리자 시간표 변경·학점 한도 변경을 추가할 때도 같은 버전 계약을 따라야 한다. 직접 SQL로 상태를 바꾸면서 version을 유지하면 보장이 깨진다.

Lua로 학생 시간표/학점/정원을 한 번에 예약하는 대안은 가능하다. 하지만 MySQL과 Redis 이중 기록의 복구·보상·영속화 순서 및 Redis Cluster hash slot 제약이 추가된다. 이번에는 MySQL을 진실의 원천으로 유지하고 Lua는 **소유자 검증과 해제**에만 쓴다.

## 락 만료와 트랜잭션

1. `SET NX PX`와 무작위 소유자 토큰으로 과목 락을 얻는다.
2. 외부 호출 뒤, DB 쓰기 전, 트랜잭션 반환 직전에 Lua로 소유권/TTL을 검증한다.
3. 감지된 만료 또는 Redis 장애는 예외를 던져 트랜잭션을 롤백한다. 외부 호출 단계에서는 아직 트랜잭션 자체가 없다.
4. **Redis TTL 만료는 DB 트랜잭션을 자동 중단하지 않는다.** 마지막 검증과 실제 commit 사이에도 만료될 수 있다. 이때 커밋 자체를 무조건 금지한다고 주장하지 않는다. DB CAS/정원 조건/UNIQUE가 겹친 실행의 정합성을 보호한다.
5. 이전 소유자의 finally는 Lua compare-and-delete이므로 새 소유자의 락을 삭제하지 않는다.
6. 커밋 후 unlock 실패는 성공 응답을 실패로 뒤집지 않고 로그를 남긴다. 남은 키는 TTL로 해제된다.

이 구현은 fencing token을 외부 시스템에서 검증하는 프로토콜이 아니다. TTL 이후 외부 호출이 중첩되는 것을 절대 금지하지도 못한다. 외부 서비스가 쓰기 작업을 수행한다면 외부에서 멱등 키·fencing을 받아 검증하거나 별도 상태 머신이 필요하다. Redis failover에서 중복 소유자가 생겨도 DB 규칙을 지키지만, 외부 동시 호출은 생길 수 있다.

## 멱등성

성공 결과를 DB에 영구 보존한다. 프로세스가 commit 후 응답 전에 죽어도 동일 키 재요청은 저장된 신청 ID를 반환한다. 동시 요청은 DB 키 제약으로 승자를 결정한다. 실패한 트랜잭션의 키도 함께 롤백되므로 같은 키로 재시도할 수 있다. 이는 **성공 효과의 멱등성**이며 모든 실패 응답을 영구 캐시하는 계약은 아니다. 읽기 전용 외부 API는 DB 재시도/동시 요청 시 여러 번 호출될 수 있다. 무기한 보존하는 키의 삭제/보관 정책은 아직 없다.
