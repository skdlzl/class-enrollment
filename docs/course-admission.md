# 과목 대기열 개선과 비교 측정

이 브랜치는 `407ddbf`의 과목 락 범위 축소 구현에서 시작합니다. 실패한 주기적 DB 조회 구현은 포함하지 않습니다.

## 변경

- 학생 분산 락으로 학생별 검증과 전체 신청 흐름을 보호합니다.
- 같은 JVM의 동일 과목 요청은 공정한 세마포어에서 대기합니다. 과목당 Redis 락 대기자는 JVM별 최대 한 명입니다.
- 입장한 요청만 새 읽기 트랜잭션에서 정원 상태를 한 번 조회합니다. 마감이면 Redis 과목 락을 얻지 않고 409를 반환합니다.
- 빈자리가 있으면 기존 과목 분산 락을 획득합니다. 저장 트랜잭션에서 정원을 다시 확인하고 신청 저장·인원 증가·커밋을 마친 후 분산 락과 로컬 입장권을 해제합니다.
- 로컬 대기와 과목 Redis 락 대기에 합계 10초의 예산을 적용합니다. DB/Redis 명령 자체의 실행 시간은 이 예산으로 강제 중단하지 않습니다.
- 입장권은 성공·거절·타임아웃·중단·오류에서 정리합니다. 대기자와 처리자가 모두 사라지면 과목 항목을 제거합니다.

로컬 세마포어는 서버 간 정합성을 보장하지 않습니다. 두 서버가 공유하는 과목 분산 락과 DB 제약이 그대로 필요합니다. 학생 락을 유지하므로 같은 학생이 서로 다른 과목을 신청해 학점·시간표 검증을 동시에 통과하는 문제도 방지합니다.

## 실행

Docker Desktop을 실행하고 기존 8080·8081 서버를 종료한 뒤 저장소 루트 PowerShell에서 실행합니다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\measure-course-admission.ps1
```

기본 JMeter 경로는 `C:\tools\apache-jmeter-5.6.3\bin\jmeter.bat`입니다. 경로가 다르면 `-JMeter "경로"`를 지정합니다.

스크립트가 빌드·테스트, MySQL/Redis 준비, 두 서버 시작, 예열, 과목 초기화, 측정, 서버 종료, 기존 과목 1 데이터 복원을 수행합니다. 기존 프로세스를 임의로 종료하지 않습니다. 다른 과목에 신청 내역이 없는 재학생 500명이 필요합니다.

같은 JAR에서 `enrollment.local-course-gate.enabled=false/true`를 비교합니다. 기본값은 false이며 측정 스크립트가 비교 대상마다 지정합니다. 각 버전은 500명·5초 ramp-up·1회 요청·정원 100·두 포트 교대 조건에서 3회 측정합니다. 실행 순서는 회차마다 바꾸고 매 실행마다 두 서버를 재시작한 후 20건 예열합니다. 두 버전 모두 요청별 timing 로그를 기록합니다.

결과는 `jmeter/results/admission-날짜시각.zip`에 저장됩니다. `summary.json`, 원본 JTL, 오류 응답 XML, 두 서버 stdout/stderr, JMeter 로그, 측정 조건, 비상 복원 SQL이 포함됩니다. 요청 수가 500인지 확인하고, 201 건수·신청 내역·enrolled_count가 일치하며 정원 이하인지 검사합니다. 정합성과 정원 충족은 구분해야 합니다. 일치하더라도 성공 100건에 미달하면 정원이 다 채워진 결과가 아닙니다.

## 해석

P95는 각 실행의 요청별 elapsed 값을 정렬한 뒤 `ceil(N × 0.95)`번째 값입니다. 평균·P95·503·201·DB 결과를 함께 평가합니다. 빠른 503이 늘어 P95만 작아지는 결과는 개선으로 채택하지 않습니다. 409는 정원 마감 응답이며 503과 구분합니다.

GitHub Actions에서도 같은 스크립트와 두 JVM을 사용합니다. CI 결과는 구현과 측정 절차의 검증이며 기존 Windows 측정과 섞어 포트폴리오 개선율을 계산하지 않습니다. 목표 환경의 반복 측정으로 P95 감소와 정합성을 확인한 후 적용 여부를 판단합니다.
