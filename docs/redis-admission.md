# Redis 락 대기 개선

이전 학점교류 실험에서 Redis의 성공 확정 P95는 5.23초였지만 집중 부하 전체 정리 평균은 244.99초였습니다. 집중 부하의 Redis 락 대기 타임아웃 4,034회와 로컬 입장 대기 타임아웃 218회가 발생했습니다. 외부 예약은 존재하는데 로컬 반영이 늦은 요청이 있으면 로컬 마감 사전 확인만으로는 새 요청을 빠르게 끝낼 수 없었습니다.

## 변경

- 강좌 락은 `SET NX PX`를 한 번만 시도합니다. 바쁘면 서버 스레드에서 Redis를 반복 조회하지 않고 DB의 RESERVING 요청을 그대로 보존해 202로 응답합니다.
- 강좌별 DB 기록 순서(created_at, id)를 사용해 새 요청의 추월을 막습니다. 외부 호출을 이미 시도한 요청은 새 요청보다 먼저 복구합니다. 사용자 클릭 시각의 전역 FIFO를 보장한다는 의미는 아닙니다.
- 복구기는 강좌별 선두와 확정/취소 작업을 찾아 32개 worker와 128개 대기 슬롯으로 처리합니다. 메모리 작업 슬롯이 가득 차면 다음 주기에 DB에서 다시 읽습니다. 원본 작업은 DB에 남습니다. 두 JVM 사이 중복 처리는 기존 DB claim과 Redis 소유권 및 외부 멱등 계약으로 제어합니다.
- 750ms의 대기 예산으로 최종 상태를 짧게 조회해 완료되면 최종 응답을 보냅니다. 이 구간에 DB 커넥션이나 Redis 락을 계속 잡지 않습니다. 개별 DB 호출 지연은 별도이므로 엄격한 HTTP 종료 시한은 아닙니다. 아직 처리 중이면 202와 Retry-After 1초를 반환합니다. 기다림 자체가 사라지는 것은 아니므로 최종 확정 지연도 측정합니다.
- 외부 호출 전에 remote_attempts를 영속 기록합니다. 외부 호출이 없었다고 증명되는 요청만 로컬에서 즉시 취소합니다. 마감 강좌의 미접촉 대기 요청은 묶어서 종료하므로 외부 취소 API를 수천 번 호출하지 않습니다.
- 비관적/낙관적 방식에서 외부 호출이 들어가는 DB 트랜잭션보다 먼저 별도 자동 커밋으로 외부 호출 의도를 기록합니다. 그렇지 않으면 롤백 때 기록도 사라져 외부 예약을 잘못 버릴 수 있습니다.
- 이전 스키마의 요청은 외부 호출 여부가 불명확하므로 마이그레이션 시 remote_attempts=1로 보존합니다. 새 요청만 0으로 시작합니다.
- 의도 저장이나 claim 획득 전 DB 연결 실패는 503과 Retry-After로 분류합니다. 이전 비교에서 관찰한 일시적 DB 장애의 HTTP 500 노출 경로를 수정했습니다.

## 안전 경계

빠른 종료 UPDATE와 외부 호출 승인 UPDATE는 같은 요청 행에서 경쟁합니다. 외부 호출 승인은 현재 owner, claim 유효기간, RESERVING 상태를 확인한 뒤 카운터를 증가시켜야 성공합니다. 이미 종료된 요청의 오래된 실행은 외부 호출을 승인받을 수 없습니다. 먼저 승인된 호출은 remote_attempts>0이므로 빠른 종료 대상이 아니며 멱등 취소/확정으로 복구합니다.

Redis TTL이 DB 트랜잭션을 자동 취소하지는 않습니다. 기존 소유권 확인과 CAS 및 UNIQUE 정합성 보호는 유지합니다. 임시 좌석을 자동 만료시키지 않는 외부 계약도 유지합니다. 영구 외부 장애가 생기면 복구 요청이 해당 강좌의 새 신청보다 우선하므로 큐가 멈출 수 있습니다. 이것은 상태를 모른 채 새 예약을 늘리는 것보다 정합성을 우선한 선택이며 운영 감시가 필요합니다.

DB 대기열은 재시작 후 유지됩니다. 동시 메모리 작업량은 제한하지만 모든 신청 기록의 영구 보존/용량 한도를 해결한 것은 아닙니다. 이번 변경은 수강신청 처리 실험이며 인증/학생별 조회 권한은 별도 범위입니다.

## 검증

기존 기능 테스트에 락 점유 중 빠른 202와 재시작 복구, 새 요청의 추월 방지, 외부 결과 불명 요청 우선 처리, 외부 미접촉 요청만 일괄 종료, DB 롤백 후 외부 호출 의도 유지, 503/Retry-After 계약을 추가했습니다.

부하 조건은 앱 2대, 동시성 128, 요청 12,000건/실험, 분산 50강좌 x 120석과 집중 1강좌 x 120석입니다. Redis를 3회씩 총 72,000건 검증합니다. 최초 202가 늘어날 수 있으므로 락 타임아웃 수만으로 성능 개선을 판단하지 않고 최초 전송부터 최종 확정까지의 지연과 전체 정리 시간을 함께 봅니다. 전후 CI 호스트가 달라 정밀한 단일 변수 인과 실험이라고 주장하지 않습니다.

외부 미접촉 취소는 외부 상태 ABSENT이고 remote_attempts=0이어야 합니다. 외부를 건드린 취소는 CANCELLED/FULL이어야 합니다. 이 구분까지 요청별 검증합니다. 워크플로 수동 실행에서는 세 전략 전체 비교를 유지하고 PR 검증에서는 수정한 Redis 경로를 실행합니다.


첫 큐 구현의 부하 실험에서는 전체 정리는 줄었지만 확정 P95가 증가했습니다. 작은 복구 worker 풀과 조회/예약/조회/확정의 정상 경로 4회 HTTP 호출, DB 데드락 뒤 고정 2초 재시도가 영향을 줄 수 있는 구조를 확인했습니다. 최종 구현은 정상 경로에서 멱등 예약과 확정을 직접 호출하고 결과 불명 재시도에서만 상태를 조회합니다. 복구 worker를 32개로 늘리고 DB 충돌은 25~100ms 지터, 외부 통신 실패는 250ms 후 재시도합니다. 요청/claim/Redis TTL 제한은 그대로 유지합니다. 복구기 전체 동시 실행과 대기 슬롯은 계속 제한됩니다.
