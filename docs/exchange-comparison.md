# 학점교류 예약의 세 전략 비교

읽기 전용 자격 조회가 아닌 실제 상태가 남는 상대 대학 좌석 예약 경로를 비교합니다. 기존 216,000건 결과와는 별도 실험입니다.

## 같은 것과 다른 것

| 항목 | 비관적 락 | 낙관적 락 | Redis |
|---|---|---|---|
| 예약 전 동시성 제어 | 강좌 SELECT FOR UPDATE | 강좌 버전 스냅샷 | JVM 입장 제어 + Redis 강좌 락 |
| 외부 조회/예약 시 DB 트랜잭션 | 열림 | 열림 | 열리지 않음 |
| 로컬 최종 보호 | 정원 조건/학생 CAS/UNIQUE | 강좌/학생 CAS/정원/UNIQUE | 강좌/학생 CAS/정원/UNIQUE |
| 외부 확정과 취소 | DB 트랜잭션 밖 | DB 트랜잭션 밖 | DB 트랜잭션 밖 |

모든 전략은 동일한 외부 상태 조회/예약/확정/취소 계약과 DB 요청 claim 및 복구 로직을 사용합니다. 커밋된 정원 마감 사전 확인도 공통 적용합니다. 마감된 요청도 취소 tombstone을 외부에 남겨 이전의 늦은 예약을 차단합니다. 낙관적 충돌로 로컬 DB가 롤백돼도 외부 예약은 되돌아가지 않으므로 동일 예약 ID를 재조회하며 재처리합니다.

이 비교는 락 하나의 마이크로벤치마크가 아닙니다. 외부 대기를 포함한 DB 트랜잭션 전략과 Redis로 외부 대기를 DB 밖으로 옮긴 전략의 전체 시스템 비교입니다. 모든 방식이 최선으로 튜닝된 유일한 구현이라고 주장하지 않습니다.

## 고정 조건

- 앱 2 JVM, 각 JVM Hikari 최대 20개, Java heap 256~512MB.
- 요청 12,000건/회, 동시성 128, 외부 기본 지연 20ms.
- 분산: 50강좌 x 정원 120 = 6,000석. 집중: 1강좌 x 정원 120석.
- 세 전략 x 두 부하 x 세 회차 = 216,000개 독립 신청. 복구 재시도와 멱등 재전송은 별도로 집계.
- 회차마다 전략 순서를 회전하며 같은 회차의 세 전략은 같은 CI runner에서 순차 실행. 회차 간 호스트 차이는 존재.
- 워밍업 없이 JVM 시작 후 측정하므로 JIT 초기 비용도 포함. 각 trial마다 앱을 재시작하고 로컬 데이터를 초기화. 상대 대학은 trial마다 다른 강좌 ID로 분리.
- 외부 저장소의 정원/학생 조회에 인덱스를 적용해 모든 전략에 동일하게 사용. 이전 단일 Redis 실험과 구현이 달라 직접적인 전후 성능 비교를 하지 않음.
- HTTP 최대 600ms, 연결 300ms, DB 풀 획득 1초, DB 락 대기 1초, DB 트랜잭션 2초, Redis TTL 3초, 요청 처리 예산 5초, claim 30초.

## 측정과 검증

첫 응답의 HTTP 200/202/409/5xx와 외부/DB/락 오류 원인을 각각 저장합니다. 202는 완료가 아닙니다. 복구기와 동일 키 클라이언트 재전송을 함께 실행해 모든 요청이 COMPLETED 또는 CANCELLED가 될 때까지 기다립니다. 처음 HTTP 요청이 유실돼 DB 행이 없는 신청도 같은 키로 다시 보냅니다.

완료 요청의 지연은 최초 클라이언트 전송 직전 시각부터 DB terminal 행 updated_at까지 계산합니다. 재시도 대기를 포함하지만 응답 네트워크 시간은 포함하지 않는 근사치입니다. 앱/DB/발생기는 같은 CI 호스트 시계를 공유합니다. 최초 응답 지연과 혼동하지 않습니다. 전체 정리 시간은 최초 제출 시작부터 모든 요청의 최종 상태를 확인할 때까지이며 조회/재전송/폴링 비용을 포함합니다.

로컬 수강신청 수, 정원 카운터, 성공 멱등 행 수, 요청별 신청 ID/학생/강좌, 상대 대학 최종 상태를 대조합니다. 100건의 멱등 키 재전송도 확인합니다. 성공 상태만 반환하고 검증을 생략하지 않습니다.

Micrometer는 파트너 action별 호출 수/시간, 재시도 cause, DB 커넥션 획득 대기/사용 시간을 수집합니다. 검증용 외부 GET 요청은 성능 지표 수집이 끝난 뒤 수행하므로 외부 호출 수에 섞이지 않습니다. 원본 응답, 재시도, 최종 DB 상태, 지표, 서버 로그를 trial별 artifact에 보존합니다.

## 재현

기존 데이터를 삭제하므로 전용 실험 DB에서만 실행합니다. 첫 실행은 빈 파트너 볼륨이 필요합니다. 같은 round-offset을 같은 외부 볼륨에서 다시 실행하면 기존 좌석이 남아 검증에 실패합니다.

```bash
mvn -f backend/pom.xml -DskipTests package
docker compose up -d --wait mysql redis external
pip install requests pymysql aiohttp
python scripts/exchange_compare.py --round-offset 0
```

### 타임아웃과 지연 원인

**비관적 락:** 집중 부하에서 DB 풀 획득 타임아웃 27,081회, SQL 오류 1205에 해당하는 DB 락 대기 재시도 7,880회가 기록됐습니다. 실제 로그에서 `total=20, active=20, idle=0`인 상태로 1,000ms 획득 제한에 걸렸고 대기 요청도 수십 개 쌓였습니다. 외부 예약 대기와 강좌 행 잠금이 커넥션 점유를 늘리는 구조와 일치합니다. 집중 부하의 회차별 전체 정리 시간은 94.99~564.14초로 변동이 컸습니다.

측정 코드에는 요청 의도 저장/claim 획득 등 일부 DB 접근이 process 내부 예외 처리 밖에 있어 커넥션 부족이 HTTP 500으로 반환되는 경로가 남아 있습니다. 이를 503으로 바꿔 기록하지 않았습니다. 일시적 DB 장애의 503 분류와 Retry-After 제공은 별도 개선 과제입니다. 오류가 난 최초 요청은 같은 키로 재전송해야 하며 복구기만으로 기록되지 않은 요청을 복구할 수 있다고 주장하지 않습니다.

**낙관적 락:** 분산 부하에서 VERSION_CONFLICT 4,134회가 기록됐습니다. DB 롤백이 외부 예약을 취소하지 않으므로 기존 예약 ID를 조회하며 재시도합니다. 정합성은 유지됐지만 성공 확정 P95는 분산 55.00초, 집중 47.51초로 길어졌습니다. 복구기의 처리 주기와 부하 발생기의 배치 재전송 대기도 이 지연에 포함되며 순수 CAS 연산 비용으로 해석하지 않습니다.

**Redis:** 집중 부하에서 REDIS_LOCK_TIMEOUT 4,034회, LOCAL_ADMISSION_TIMEOUT 218회, REQUEST_DEADLINE 110회가 기록됐습니다. 최종 오류 대신 처리 중으로 유지하고 복구했으므로 HTTP 500이 0건이어도 내부 타임아웃은 존재합니다. 집중 부하의 성공 확정 P95는 세 회차 각각 5.07/5.27/5.37초였지만 합산 P99는 52.10초입니다. 전체 정리는 회차별 87.32~432.59초로 길고 변동이 컸습니다.

Redis는 강좌별 예약 구간을 순차화합니다. 외부 임시 좌석은 확보됐으나 로컬 반영이 지연된 요청이 있으면 로컬 정원 마감 사전 확인만으로 외부 마감을 알 수 없습니다. 이런 상태와 강좌 락 대기가 함께 정리 지연을 키울 수 있습니다. 원본에서 늦게 완료된 Redis 신청의 RESERVING 상태와 외부 응답 타임아웃을 확인했고 락 대기 이벤트도 계측했습니다. 다만 서버 내부 모든 구간을 추적한 것은 아니므로 각각의 기여 시간을 단정하지 않습니다. 외부 마감 응답의 안전한 공유와 복구 요청의 처리 우선순위가 후속 개선 후보입니다.

**외부 API:** 집중 부하의 응답 타임아웃은 비관적 1,793회, 낙관적 866회, Redis 2,043회입니다. HTTP 최대 응답 제한은 600ms입니다. 설정된 20ms 지연에 서버 큐/SQLite 처리/네트워크/공유 CI 호스트 비용이 추가될 수 있습니다. 외부 내부 타이밍이 없으므로 특정 항목을 근본 원인이라고 단정하지 않습니다. Redis의 파트너 연결 타임아웃 12회는 응답 타임아웃과 별도입니다. 분산 실험에는 REDIS_UNAVAILABLE 1회도 있었고 복구됐습니다.

타임아웃 이벤트 수, 최초 처리 중 응답 수, 서버 오류 수는 다른 지표입니다. 동일 요청이 여러 번 실패할 수 있습니다. 취소 중 lastError는 원래 거절 이유(COURSE_FULL 등)를 유지하므로 initial_pending_causes를 통신 실패 원인으로 그대로 읽으면 안 됩니다. 실제 재시도 원인은 metrics의 exchange.retries 및 서버 로그를 사용합니다.

### 채택 판단

**인기 강좌의 신청 확정 지연과 DB 자원 압박 및 최초 서버 오류 억제를 우선하면 Redis 채택 근거가 있습니다.** 집중 부하에서 비관적 락 대비 성공 확정 P95는 약 97.9% 짧았고 DB 커넥션 획득 대기 누적은 약 99.5% 적었습니다. DB 풀 획득 타임아웃과 최초 HTTP 500은 0건이었습니다.

그러나 모든 성능 지표에서 Redis가 최고는 아닙니다. 분산 부하 성공 P95는 비관적 락 1.56초가 Redis 2.08초보다 짧습니다. 집중 부하의 전체 요청 정리는 낙관적 락 평균 65.96초가 Redis 244.99초보다 빠릅니다. Redis는 집중 부하의 전체 거절/취소 처리까지 최적화된 상태가 아닙니다. 따라서 채택 이유를 ‘성능이 무조건 가장 좋다’로 쓰지 않고 **‘신청 확정 지연과 DB 보호를 우선한 선택이며 마감 요청 대기는 남은 과제’**로 명시합니다.
