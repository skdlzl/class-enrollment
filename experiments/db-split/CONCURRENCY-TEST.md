# 동시성 테스트

## 문제 재현
같은 알림을 두 서버가 동시에 처리할 때 둘 다 미발송 상태를 읽으면 API가 중복 호출될 수 있습니다.
모의 API를 사용하는 별도 JVM 두 개로 재현합니다. 무보호 구성은 두 서버가 PENDING을 읽은 뒤 테스트용 장벽에서 기다리게 합니다. 장벽 해제 후 각각 API를 호출합니다. 이 경로는 테스트 소스에만 존재합니다.

## 제어 방식 비교
비관적 락, 버전 기반 낙관적 락, Redis 분산 락 구성을 같은 알림의 동시 요청으로 검증합니다. 보호 구성의 장벽은 보호 로직 진입 전에 둡니다. DB 락 안에 장벽을 두면 두 요청이 장벽에 도달할 수 없기 때문입니다.
Redis 구성에는 DB 처리 상태와 소유자 검사가 함께 적용됩니다. 세 구성 모두 동일한 외부 API 멱등 키를 사용합니다.

## 검증 기준
각 구성별 새 알림 하나로 3회 반복합니다. 무보호는 API 호출 2회, 보호 구성은 1회를 기대합니다. 모의 API의 실제 발송 효과는 멱등 키 때문에 모두 1회여야 합니다. 완료 후 재요청은 추가 API 호출 없이 종료해야 합니다.
이것은 특정 경쟁 순서를 강제하는 기능 테스트입니다. 동시성 버그의 발생 확률이나 성능을 측정하지 않습니다. 서버 강제 종료와 Redis 장애는 이 테스트 범위가 아닙니다.

```powershell
& .\experiments\db-split\scripts\run-notification-tests.ps1 -Concurrency
```

Docker Desktop만 필요합니다. 두 테스트 JVM과 컨테이너는 자동 관리되며 실험 결과는 notifications-*.zip에 저장됩니다. notification-concurrency.json의 passed와 apiCalls, providerUniqueEffects, apiCallsAfterReplay를 확인하세요. 실행 전에는 기대값을 실측 결과로 쓰지 않습니다.

## 포트폴리오 초안
**문제** 같은 알림을 여러 서버에서 동시에 처리하면 외부 API가 중복 호출될 수 있어 알림 단위 동시성 제어가 필요했습니다.

**설계** 비관적 락, 낙관적 락, Redis 분산 락을 적용해 처리 권한을 획득한 요청만 API를 호출하도록 구성했습니다. 장애 후 재시도에는 DB 상태 관리와 API 멱등 키를 함께 사용했습니다.

**검증** 무보호 상태의 중복 호출을 먼저 재현하고 각 보호 구성에서 API 호출 횟수와 완료 후 재요청을 검증합니다. 이 재현 테스트의 결과 수치는 실행 후 기입합니다.

**성능 비교** 별도 기존 부하 실험에서 모든 알림을 두 번 전달했을 때 세 구성 모두 매회 알림 1000건을 완료했고 API도 1000회 호출했습니다. 완료 P95의 3회 평균은 비관적 락 118.69초, 낙관적 락 57.78초, Redis 58.16초였습니다. Redis의 비관적 락 대비 51.0% 감소는 API 응답까지 행 락을 유지한 구성과의 비교이며 일반적인 속도 우위를 의미하지 않습니다. 완료 시간에는 부하 생성기의 대기가 포함됩니다.
